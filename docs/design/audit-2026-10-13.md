## Platform Conformance Verdict

**PASS: this is a native Mac app, not a ported website.** A fluent Mac user will trust most of it:

- The popover is a real `MenuBarExtra(.window)` with the system's own material.
- The window is a `NavigationSplitView` with a unified toolbar and a segmented Log/Settings switch.
- Forms are grouped `Form`s with system toggles, pickers, and `DisclosureGroup`.
- App settings are a real `Settings` scene.
- The log is an `NSTextView` with the standard find bar.
- Icons are SF Symbols only, and there is no hand-made glass, gradient, or shadow.
- Destructive delete uses Undo instead of a dialog.
- The editor asks Save / Discard / Cancel.

It is not yet fully conformant. These are the specific violations:

1. **Not every action is reachable from the menu bar.** Clear Log, Copy All, Export Log…, Jump to Latest, the Log/Settings switch, Move to Group, New/Rename/Delete Group, and reordering exist only in the toolbar, a context menu, a hover control, or by drag (P1).
2. **⌘⌫ is bound to Delete Command app-wide.** In any text field, ⌘⌫ is the standard "delete to start of line". Here the menu takes the keystroke first and deletes (and stops) the selected command instead (P1).
3. **Feedback is tied to the popover.** Banners and port-conflict notices only exist in the popover. An action in the window that fails, or is blocked, gives no visible response there (P1 x2).
4. **Selection is a custom accent wash (`.selection.opacity(0.22)`), not the system selection highlight** that spec 4.2 asks for (P2).
5. **The popover's group Start All / Stop All is a hover-only affordance** (P2). The ios.md slop test names "hover-dependent affordances".

### P1 Major

#### [P1-1] Error banners render only in the popover, so failures that start in the window are invisible

- **Location**:
  - The banner is drawn only at `Sources/AmpersandApp/Views/CommandBarView.swift:16-20`. `InlineBanner` has no other call site (verified with grep).
  - Banners raised from window actions:
    - `Window/MainWindow.swift:124`: log export failure.
    - `Model/AppModel.swift:283`: config export failure.
    - `Model/AppModel.swift:291`: config import failure.
    - `Model/AppModel.swift:328`: save blocked by read-only config.
    - `Model/AppModel.swift:333`: config save failure. This is reached from the editor sheet's Save (`Window/CommandEditorSheet.swift:74-79`) and the Settings tab's Save (`Window/CommandSettingsPane.swift:34-38`).
- **Category**: Conformance (feedback) / Adaptivity (surface context)
- **Impact**: The user is in the window when they save, export, or import. The popover is closed, so the banner draws nowhere they can see. `show(_:)` clears all of these except the save failure after 8 s (`AppModel.swift:307-315`), so the user never sees them at all. A failed save is worse: `CommandEditorSheet.save()` closes the sheet and selects the "saved" command, so the UI says it worked while `config.json` was never written. This breaks principle 2, "Failure is loud", and spec 4.6, "errors name the problem and the recovery".
- **Guideline**: HIG, Feedback: report the outcome where the action happened. A window-originated error belongs in that window (an inline message, or an alert or sheet for a blocking failure).
- **Recommendation** (code level):
  1. Draw the same banner at the top of the window's detail column:
     ```swift
     // MainWindow.swift, on the NavigationSplitView (after line 21)
     .safeAreaInset(edge: .top, spacing: 0) {
         if let banner = model.banner {
             InlineBanner(banner: banner, model: model)
                 .padding(.horizontal, 12).padding(.vertical, 8)
         }
     }
     ```
  2. Make saving report its result. Change `persist()` to `@discardableResult private func persist() -> Bool` and `save(_:)` to `@discardableResult func save(_ spec: CommandSpec) -> Bool`. In `CommandEditorSheet.save()`, only call `close()` when `model.save(spec)` returns `true`. Otherwise keep the sheet open: the banner is now visible behind it, or you can add an `.alert` bound to a failure message.
  3. Do not auto-dismiss error banners. Pass `autoDismiss: false` at `AppModel.swift:283` and `:291` and `MainWindow.swift:124`, like `:333` already does.
- **Suggested command**: `/impeccable harden`

#### [P1-2] A blocked start (port in use) is silent everywhere except the popover's expanded row

- **Location**:
  - `Model/AppModel.swift:118-121` sets `runtime.portConflict` and returns without changing `status`.
  - The only place that draws it is `Views/ExpandedRow.swift:20-28`, which shows only for the selected popover row.
  - Start paths that never show it:
    - window toolbar `Window/MainWindow.swift:65-66`
    - Command menu `Commands/AppCommands.swift:30-34`
    - collapsed row hover button `Views/CommandRow.swift:29-38`
    - context menu `Views/CommandContextMenu.swift:10`
    - Start All `Views/CommandBarView.swift:209, 220`
  - The same limit applies to the `.failedToStart` detail (`ExpandedRow.swift:29-34`), "Restart to Apply" (`:35-40`), and the health failure reason (`:41-46`). The window does show a short subtitle stamp for `.failedToStart`, but none of the others.
- **Category**: Conformance (feedback) / Accessibility
- **Impact**: The user clicks Start and the glyph stays a hollow "stopped" circle, with no message or sound. This is the most common failure for this user (a port-forward or dev server already bound to its port). It breaks spec 4.6's "visual feedback within 100 ms of any action" and gives no way to find the recovery ("Start Anyway" or "Kill pid N"). VoiceOver says nothing either, because the conflict is not part of `CommandRow.accessibilityText` (`CommandRow.swift:88-98`).
- **Guideline**: HIG, Feedback. Spec 4.5 lists "port in use" as a row state to design.
- **Recommendation** (code level):
  1. Move the `notices` block out of `ExpandedRow` into its own view, `CommandNotices(runtime:model:)`, and put it in the window as well:
     ```swift
     // MainWindow.swift CommandDetail.body, on the Group (line 47)
     .safeAreaInset(edge: .top, spacing: 0) {
         CommandNotices(runtime: runtime, model: model)
             .padding(12)
             .frame(maxWidth: .infinity, alignment: .leading)
             .background(.bar)
     }
     ```
  2. In the popover, select the row when a conflict is found, so it expands and shows the notice. At `AppModel.swift:120`, add `popoverSelection = id` after setting `runtime.portConflict = owner`.
  3. In collapsed rows, show the conflict in place of the metrics. In `CommandRow.trailing`, check it first: `if let owner = runtime.portConflict { Text("port in use · \(owner.name)") }`. Also add `"port \(port) in use by \(owner.name)"` to `accessibilityText`.
- **Suggested command**: `/impeccable harden`

#### [P1-3] Command ▸ Delete is bound to ⌘⌫, which takes over a standard text-editing key

- **Location**: `Sources/AmpersandApp/Commands/AppCommands.swift:67-71` (`.keyboardShortcut(.delete)`, which is ⌘⌫).
- **Category**: Conformance (keyboard) / Accessibility
- **Impact**: On macOS, ⌘⌫ in any text field means "delete to beginning of line". AppKit offers Command-key events to the main menu before the first responder's `keyDown`. So when the user edits a name, command line, or env text in the window's Settings tab, ⌘⌫ deletes the selected command and stops its process, and the line is not deleted. The same applies to the group rename field (`Sidebar.swift:77`). When the window is open, the app is `.regular` and its main menu is live, so it may also fire from the popover's filter field. There it acts on the **window** selection, not the popover selection.

  Undo restores the configuration but, by design, does not restart the process (spec 4.5). There is also a trap: while a text field has focus, `undo()` (`AppCommands.swift:76-79`) sends `undo:` to the text view, not to the model, so ⌘Z does not bring the command back until focus leaves the field. You already guard Undo/Redo this way; Delete needs the same guard.
- **Guideline**: HIG, Keyboard shortcuts: don't override the standard text-editing shortcuts that people rely on.
- **Recommendation** (code level), the same pattern as `undo()`:
  ```swift
  Button("Delete") {
      if isEditingText {
          NSApp.sendAction(#selector(NSResponder.deleteToBeginningOfLine(_:)), to: nil, from: nil)
      } else if let selected, NSApp.keyWindow?.identifier?.rawValue.hasPrefix("main") == true {
          model.delete(selected.id)
      }
  }
  .keyboardShortcut(.delete)
  ```
  Use whatever check identifies the main window. The point is to act only when the main window is key and no text is being edited. Apply the same `isEditingText` guard to `Start/Stop` (⌘↩) and `Duplicate` (⌘D) for safety.
- **Suggested command**: `/impeccable harden`

#### [P1-4] Several actions cannot be reached from the menu bar

- **Location**:
  - Log actions are toolbar-only: Clear (`Window/MainWindow.swift:91`), Copy All (`:92`), Export… (`:93`). Jump to Latest is an overlay button only (`:84-87`).
  - The Log / Settings switch is a toolbar segmented control only (`MainWindow.swift:56-63`), with no shortcut. Show Log (⌘L) covers one direction, but nothing selects Settings.
  - Move to Group is only in the context menu (`Views/CommandContextMenu.swift:20-28`).
  - New Group is a sidebar button (`Window/Sidebar.swift:43-47`). Rename… and Delete Group are only in the group header context menu (`Sidebar.swift:89-98`). Start All / Stop All for a group is in context menus and on hover; the menu's "Start/Stop Group" covers the selected command's group only.
  - Reordering is drag only (`Sidebar.swift:17-20`). There is no keyboard or menu way to do it.
  - Save in the Settings tab has ⌘S (`CommandSettingsPane.swift:43`) but no File ▸ Save menu item, so the shortcut cannot be discovered.
- **Category**: Conformance
- **Impact**: Spec 4.3 states the rule "HIG: every action reachable from the menu bar", and this audit was told to check it. Keyboard-only and VoiceOver users have to find toolbar items or context menus. Reordering cannot be done at all without a mouse drag.
- **Guideline**: HIG, The menu bar: "Make every command available in the menu bar".
- **Recommendation** (code level): lift `copyAll()` and `export()` from `CommandDetail` into `AppModel`, together with `follow` as `logFollow: Bool`, so the menus can call them. Then extend `AppCommands`:
  ```swift
  CommandGroup(before: .toolbar) {                       // View menu
      Toggle("Log", isOn: Binding { model.windowTab == .log } set: { if $0 { model.windowTab = .log } })
          .keyboardShortcut("1")
      Toggle("Settings", isOn: Binding { model.windowTab == .settings } set: { if $0 { model.windowTab = .settings } })
          .keyboardShortcut("2")
      Divider()
      Button("Jump to Latest") { model.logFollow = true }.keyboardShortcut(.downArrow, modifiers: [.command])
      .disabled(selected == nil)
  }
  // in CommandMenu("Command"), after Open in Browser:
  Divider()
  Button("Clear Log") { if let selected { model.clearLog(selected.id) } }.keyboardShortcut("k")
  Button("Copy Log") { if let selected { model.copyLog(selected.id) } }.keyboardShortcut("c", modifiers: [.command, .option])
  Button("Export Log…") { if let selected { model.exportLog(selected.id) } }
  Divider()
  Menu("Move to Group") { /* same body as CommandContextMenu lines 21-27 */ }
  Button("Move Up")   { if let selected { model.moveUp(selected.id) } }.keyboardShortcut(.upArrow, modifiers: [.command, .option])
  Button("Move Down") { if let selected { model.moveDown(selected.id) } }.keyboardShortcut(.downArrow, modifiers: [.command, .option])
  Divider()
  Button("New Group") { model.requestNewGroup() }
  Button("Rename Group…") { … }.disabled(selected?.spec.group == nil)
  Button("Delete Group") { … }.disabled(selected?.spec.group == nil)
  // in CommandGroup(replacing: .newItem) or .saveItem:
  Button("Save") { model.saveCurrentSettingsDraft() }.keyboardShortcut("s")
  ```
  `moveUp` and `moveDown` wrap `ConfigEditor.reorder`. Saving the draft needs the draft to live in the model, or a `FocusedValue` published by `CommandSettingsPane`. Using `@FocusedValue` is the cleaner SwiftUI way to share the Settings-tab draft with the menu.
- **Suggested command**: `/impeccable adapt`

### P2 Minor

#### [P2-1] Return does nothing right after typing a filter

- **Location**: `Views/CommandBarView.swift:152-156`. The filter never selects the first match.
- **Category**: Conformance (contract)
- **Impact**: The contract's thesis is "driven like Spotlight … Return to act". The user types `web` and presses Return, and nothing happens until they press ↓.
- **Recommendation**: add `.onChange(of: filter) { if !visibleRuntimes.contains(where: { $0.id == model.popoverSelection }) { model.popoverSelection = visibleRuntimes.first?.id } }` on the header. Only do this while `filter` is not empty, so the bare popover still opens collapsed.
- **Suggested command**: `/impeccable harden`

#### [P2-2] Popover keyboard handling only works while the filter field has focus

- **Location**: `Views/CommandBarView.swift:47`. `.onKeyPress` is attached to the `TextField`.
- **Category**: Accessibility (keyboard)
- **Impact**: With Full Keyboard Access on, Tab moves focus to the expanded row's buttons, the footer, or the Add menu. After that, ↑/↓/↩/⌘R/⌘L stop working.
- **Recommendation**: move `.onKeyPress(phases: .down, action: handleKey)` from line 47 to the outer `VStack` (after line 26). Key presses bubble up from the focused child to its ancestors, so the handler then covers every focusable child.
- **Suggested command**: `/impeccable harden`

#### [P2-3] Start feedback waits for `lsof`

- **Location**: `Model/AppModel.swift:117-125`. `PortProbe.owner` (which runs `/usr/sbin/lsof`, `AmpersandCore/Monitoring/PortProbe.swift:12-27`) is awaited before `supervisor.start()` sets `.starting`.
- **Category**: Performance
- **Impact**: For every command with a port, the glyph stays "stopped" until `lsof` finishes, which often takes longer than 100 ms. That breaks spec 4.6, "status flips to dashed starting immediately". A second Return in that gap starts a second probe.
- **Recommendation**: add `var isStartPending = false` to `CommandRuntime`. Set it at the top of `start(_:)`, clear it after the probe, and let `StatusGlyph` draw `circle.dashed` while it is true. Guard re-entry with `guard !runtime.isStartPending`.
- **Suggested command**: `/impeccable optimize`

#### [P2-4] Popover selection is a custom tint, not the system highlight

- **Location**: `Views/CommandRow.swift:47-51` (`.fill(.selection.opacity(0.22))`).
- **Category**: Theming / Conformance
- **Impact**: Spec 4.2 says "Selection uses the system list selection highlight". A 22% wash is weaker than the system highlight and does not strengthen under Increase Contrast. The secondary text on it also does not switch to the variant meant for a selected background.
- **Recommendation**: `.background(isSelected ? AnyShapeStyle(.selection) : AnyShapeStyle(.clear), in: .rect(cornerRadius: 8, style: .continuous))` plus `.environment(\.backgroundProminence, isSelected ? .increased : .standard)`. This makes `.secondary` and the log tail adapt the way they do in a system `List`.
- **Suggested command**: `/impeccable polish`

#### [P2-5] The group Start All / Stop All button is hover-only

- **Location**: `Views/CommandBarView.swift:208-212`. The header has no accessibility action.
- **Category**: Accessibility / Conformance
- **Impact**: VoiceOver and Full Keyboard Access users cannot see this control. They can only get to it through the context menu (VO-Shift-M) or ⌥↩, which nothing tells them about.
- **Recommendation**: on the `HStack` at line 202, add `.accessibilityElement(children: .combine)` and `.accessibilityAction(named: anyActive ? "Stop All" : "Start All") { model.toggleGroup(group.id) }`. Either show the button all the time at `.secondary` weight, or keep it in the layout with `.opacity(hovering ? 1 : 0)`, which also avoids a layout shift.
- **Suggested command**: `/impeccable harden`

#### [P2-6] State text drawn in `.tertiary`

- **Location**: `Views/CommandRow.swift:84` (the "stopped" / "couldn't start" state word) and `Views/ExpandedRow.swift:54` ("No output yet.").
- **Category**: Accessibility (contrast)
- **Impact**: The tertiary label colour is about 25% opacity. On the popover material that is well below 4.5:1 (craft-floor), and these texts carry real state.
- **Recommendation**: use `.secondary`. The difference in weight against the name is enough.
- **Suggested command**: `/impeccable polish`

#### [P2-7] Yellow warning glyphs are hard to see in light mode

- **Location**: `Views/StatusGlyph.swift:23-26` (health badge `.yellow`, `.imageScale(.small)`, offset over the green dot) and `Window/EnvEditor.swift:29`.
- **Category**: Theming / Accessibility
- **Impact**: `systemYellow` on a light background is well under 3:1 for a non-text graphic. The health-failing badge is the only signal of that state in a collapsed row.
- **Recommendation**: use `.symbolRenderingMode(.multicolor)` on `exclamationmark.triangle.fill` (yellow with a dark exclamation mark). Add a knockout so the badge separates from the green dot: `.background(Circle().fill(.background).padding(-1))`.
- **Suggested command**: `/impeccable polish`

#### [P2-8] A long name can truncate the exit stamp

- **Location**: `Views/CommandRow.swift:16-28` and `:68-71`. The name and the trailing `TimelineView` compete with the same layout priority. The stamp has `.lineLimit(1)`.
- **Category**: Adaptivity (popover sizing)
- **Impact**: At 360 pt, the stamp `exit 1 · 14:02 · retry in 4s` plus a long name plus a port means both get cut. The contract's "memorable moment" is that stamp.
- **Recommendation**: `.layoutPriority(1)` on the `TimelineView` (line 26) so the name, which already truncates in the middle, gives way first.
- **Suggested command**: `/impeccable layout`

#### [P2-9] Errors and information share one banner icon

- **Location**: `Views/InlineBanner.swift:10-11` (always `info.circle`, `.secondary`). `Banner` (`Model/AppModel.swift:5-10`) has no severity.
- **Category**: Conformance (feedback)
- **Impact**: "Couldn't save your changes" looks the same as "Cleaned up 2 processes". That conflicts with "failure is loud".
- **Recommendation**: add `enum Kind { case info, error }` to `Banner`. For `.error`, use `exclamationmark.triangle.fill` with `.symbolRenderingMode(.multicolor)`.
- **Suggested command**: `/impeccable clarify`

#### [P2-10] Delete Group has no Undo

- **Location**: `Window/Sidebar.swift:97` → `Model/AppModel.swift:275-279`. No undo is registered.
- **Category**: Conformance
- **Impact**: Spec 4.6 says "Destructive actions use Undo". Deleting a group loses its name and membership for good.
- **Recommendation**: capture `config.groups` and the members' `group` values before deleting, then `undoManager.registerUndo` to put them back and `setActionName("Delete Group “\(name)”")`.
- **Suggested command**: `/impeccable harden`

### P3 Polish

- **[P3-1] The Reduce Motion fallback is "no animation", not a crossfade.** `CommandBarView.swift:27-28` passes `nil`, so the `.opacity` transition at `CommandRow.swift:42` snaps. The contract asks for a crossfade. Use `reduceMotion ? .easeInOut(duration: 0.15) : .snappy`. (`/impeccable animate`)
- **[P3-2] Hovering a row shifts its metrics.** The hover button at `CommandRow.swift:29-38` is inserted into the `HStack`, which pushes CPU, memory, and uptime about 20 pt to the left. That breaks "update in place with no layout shift". Keep the button in the layout with `.opacity(hovering && !isSelected ? 1 : 0)`, `.allowsHitTesting(...)`, and `.accessibilityHidden(...)`. (`/impeccable polish`)
- **[P3-3] Inconsistent "add" copy.** File menu "New Command" (`AppCommands.swift:14`), sidebar "New Command…" (`Sidebar.swift:35`), popover and empty state "Add Command…" (`CommandBarView.swift:123`, `EmptyStateView.swift:13`). Pick one. (`/impeccable clarify`)
- **[P3-4] Undo and Redo use fixed titles, and Redo never works.** `AppCommands.swift:22-27` always shows "Undo" or "Redo" and is never disabled. `AppModel.restore` (`:238-242`) registers no redo, even though `setActionName` is already called (`:235`). Use `model.undoManager.undoMenuItemTitle` and `.disabled(!canUndo)`, and register the inverse in `restore`. (`/impeccable polish`)
- **[P3-5] The window subtitle is a frozen countdown.** `MainWindow.swift:54, 76-78` computes the stamp with `Date()` and no timeline, so "retry in 4s" never counts down. Wrap it in `TimelineView(.periodic(from: .now, by: 1))`, or drop the countdown from the subtitle. (`/impeccable polish`)
- **[P3-6] The Clear Log toolbar button uses the trash symbol** (`MainWindow.swift:91`). It sits next to Start, Stop, and Restart and reads like "Delete command". Use `clear` or `xmark.circle`. (`/impeccable clarify`)
- **[P3-7] Settings glitches.** In `AppSettingsView.swift:16-23`, setting `launchAtLogin` back inside its own `onChange` fires a second `setEnabled`, which can replace the first error message. Notification status is read only once in `.task` (`:44`), so "Open System Settings" stays visible after the user fixes it there. Refresh it on `NSApplication.didBecomeActiveNotification`. (`/impeccable harden`)
- **[P3-8] Probable shortcut clash: ⌘E.** Edit… (`AppCommands.swift:60`) uses ⌘E. `TextEditingCommands()` (`:39`) normally adds Find ▸ "Use Selection for Find" on ⌘E. Confirm in the running app's menu. If both are there, move Edit… to ⌘I or ⇧⌘E. (`/impeccable polish`)

## Patterns & Systemic Issues

- **The popover is the only place that gives feedback.** Banners, port conflicts, start failures, "Restart to Apply", and health reasons all live in `CommandBarView` and `ExpandedRow`, and the window has none of them (P1-1, P1-2). The model already holds this state centrally. It just needs one shared view (`InlineBanner` + `CommandNotices`) placed on both surfaces.
- **Window actions live in the toolbar and context menus, with only a partial copy in the menu bar** (P1-4). `CommandContextMenu` already lists everything. The Command menu should mirror it, plus log and group items.
- **Keyboard handling is attached to single views** (popover key handler on the text field, P2-2; ⌘⌫ with no text-editing guard, P1-3). Shortcuts need one deliberate place to live and one rule for when text editing wins.
- **Hover-only controls** (group Start All, P2-5; row start button that also shifts the layout, P3-2): both need to stay in the layout and have an accessibility action.

## Positive Findings

Keep these and repeat them:

- **Semantic colour throughout.** No raw hex in any view. Status colours are system `.green/.orange/.red`. Surfaces use `.fill.tertiary/.quaternary`, `.separator`, `.background`, `.textBackgroundColor`. ANSI colours map to system colours where one exists (`LogView.swift:28-39`).
- **System materials only.** The popover is `MenuBarExtra(.window)` with no hand-made glass, gradient, or shadow anywhere.
- **The status vocabulary works by shape.** `StatusGlyph` uses filled, dashed, octagon, and hollow SF Symbols, with colour as a second signal. The menu bar `&` is a template image whose attention state is a dot (shape), not red.
- **VoiceOver basics are right.** Each collapsed row is one element with its state in words (name, state, port, CPU, memory, uptime, stamp) plus Start/Stop, Restart, and Show Log custom actions (`CommandRow.swift:57-62`). Group headers have `.isHeader`. Icon-only buttons have labels. The menu bar label reads "Ampersand, 4 running, 1 crashed".
- **Reduce Motion is checked** in both places that animate (`CommandBarView.swift:11, 27-28`, `CommandRow.swift:10, 42`).
- **Tabular figures** (`.monospacedDigit()`) on every live number. SF Mono is used only for command lines, log lines, and env text, exactly as spec 4.6 says.
